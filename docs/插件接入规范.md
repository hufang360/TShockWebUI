# 插件接入规范

本仓库把「第三方 / 自研 TShock 插件」的能力做成可选模块。每接入一个插件，写**一篇**
`docs/插件-<插件名>.md`：接入细节（端点 / 字段 / 权限 / 限制）+ 页面信息（用到的
REST API / 指令、依赖插件版本、项目地址）。模板见第 1 节。

## 0. 铁律（所有插件通用）

1. **不虚构 API**：端点、字段、权限必须来自插件源码或实测，写进文档并注明出处。
2. **不提权**：浏览器只持同源 `/api/*`；TShock token 只在后端内存。所有请求用**当前登录玩家
   自己的 token**，权限由插件判定。
3. **插件缺失/无权限要提示**，不能让界面报错或空白：
   - 探测端点 404 → `plugin_not_installed`（前端 `plugin_missing`）
   - 403 → `no_permission`
4. **单容器、单端口**，只暴露固定的 `/api/*`，不做通用 URL 代理。
5. **模块默认不显示**：需在「设置 → 激活模块」探测到插件后手动打开，入口才进侧边栏。
6. **按服务器分开记忆**：模块开关（`tswui:modules`）与界面状态（`tswui:moduleState`）都以
   `X-TSWUI-Target` 对应的 `serverId` 为键——不同服务器装的插件不同。

## 1. 统一模板（每个 `docs/插件-<名>.md` 用这套标题）

```markdown
# <插件名>（<插件包名>）

## 0. 插件依赖
- 插件版本（集成验证版本）、项目地址（GitHub）、权限、配置目录、探测方式

## 1. 插件是什么 / 依赖什么
- 用途、指令、源码出处、REST 端点前缀

## 2. 上游 REST 端点（事实来源）
| 端点 | 参数 | 权限 | 说明 |

## 3. 本仓库后端接口
| /api/... | 对应上游 | 说明 |

## 4. 前端模块
- 激活方式、侧边栏入口、页面结构、默认焦点等交互约定

## 5. 数据字段
- 上游字段 → 本仓库 `FishGood`/`PlayerLook` 等同名字段（含容错）

## 6. 权限与限购
- 用户组权限、allowGroup/allowPlayers/denyPlayers 等限制如何展示

## 7. 已知限制 / 坑
- 版本差异、字段类型陷阱、实测结论

## 8. 验证命令
- curl / 端到端脚本
```

> **§3 只写映射**：`/api/...` ↔ 上游端点，以及本插件特有的偏差（前缀回退、探测方式、限额）。
> 参数、响应字段、错误码、SSE / 降级细节一律以 [`API_SPEC.md`](API_SPEC.md) 为准，这里不复述
> （两处都写必然漂）。§2 写的是**上游**插件的真实端点（事实来源＝插件源码 / 实测）。

## 2. 通用实现位置（Cheat sheet）

| 关注点 | 位置 |
| --- | --- |
| 上游客户端（探测 + 调用 + 错误分类） | `server/internal/tshock/<plugin>.go` |
| `/api/*` 路由与 handler | `server/internal/api/handlers.go` |
| 前端传输层契约 | `web/src/lib/transport.ts`（类型 + `BackendTransport`） |
| 真实/Mock 实现 | `web/src/lib/httpTransport.ts` / `mockTransport.ts` |
| 模块开关 | `web/src/lib/modules.ts` + `web/src/pages/SettingsPage.tsx` |
| 按服务器记忆界面状态 | `web/src/hooks/useModuleState.ts` |
| 测试桩 | `web/src/test/playerStubs.ts` |

### 统一能力矩阵（`GET /api/capabilities`）

前端**不要再各打一遍** `*/capabilities`：启动、首页、设置页统一读 `/api/capabilities`
（`transport.capabilities(fresh?)`），一次返回 `messenger / batch / player / fish / requests / webauth`，
各字段与对应分端点同构；`reachable=false` 表示上游不可达（此时别按「缺插件」隐藏模块）。
后端实现：`server/internal/api/capabilities.go`（各 `probe*` 函数与分端点共用）。
新增可选插件时：加一个 `probe*` + 响应字段 + `web/src/lib/transport.ts` 的 `ServerCapabilities`。

### 能力探测（capability）约定

- 后端用**只读**调用探测：优先用**消费端真在用的那个端点**（如 FishShop 直接读一次
  `/fishshop/list`）；没有合适端点时才用缺参数的调用（如 `/pm/look` 空 name）。
  不要为了探测而故意发缺参请求——靠「少参数 → 400」反推「端点在」是借报错当探测。
- 404 = 未安装，403 = 无权限，2xx = 已安装。
- **400 分两种**：如果该端点的 400 只有业务含义（如 FishShop 「商店打烊」），那就是**已安装**，
  文案留给实际数据接口原样展示；如果 400 就是「缺参数」（探测专用），也不应当成失败。
- **只有已发布的旧地址才做回退**：先试当前地址，404 再回退旧地址，成功的前缀按上游地址缓存。
  从未向外发布过的历史前缀（如 FishShop 的 `/v3/fishshop/*`）**不复**——那会让每次调用都多打一次 404。
  两个地址都 404 且能断定是「插件版本过旧」时，返回 `plugin=true, rest=false` + `501 plugin_outdated`，
  而不是笼统的「未安装」。
- 返回 `{ "plugin": bool, "rest": bool, "permission": bool }`（PlayerManager 无 `rest` 字段），
  前端据此禁用模块开关 / 区分「未安装」与「版本过旧」。

### 协议握手（自研信使插件通用）

自研插件与后端是同一套代码库、会一起迭代，必须能判定「装没装 / 什么版本 / 哪条协议 / 有哪些能力」，
而不是拿 404 统一当「未安装」。约定：

1. **插件暴露 `GET /webui/meta`**（无需 token，可带 `secret`）：
   ```json
   { "name": "WebUI", "version": "0.1.0", "protocol": 1, "minProtocol": 1,
     "capabilities": ["batch", "chat", "commands", "data", "events", "me", "serverinfo", "sessions"] }
   ```
2. **后端声明 `BackendProtocol`**（`server/internal/tshock/meta.go`）。兼容 = `minProtocol ≤ BackendProtocol ≤ protocol`。
3. **改动规则**：
   - **新增端点 / 字段**（向后兼容）→ 只把一个能力加进 `capabilities`，**不动协议号**；
   - **改动既有字段 / 语义**（破坏性）→ 两侧 `protocol` 一起 +1，并把 `minProtocol` 设为仍能兼容的最旧后端协议。
4. **后端错误分类**：某端点 404 时，用 `/webui/meta` 区分——
   - meta 404 → `plugin_not_installed`（旧插件或未安装，无法区分）；
   - 协议不兼容 → `plugin_protocol_mismatch`；
   - 能力缺失 / 端点与声明不一致 → `plugin_outdated`（`message` 含版本与能力名）。
5. **诊断入口**：`GET /api/plugin/status` + 设置页「信使插件诊断」，一眼看到两侧版本 / 协议 / 能力。
6. **容错习惯**：新增字段一律给默认值；解析上游 JSON 时容忍缺字段（用零值），不要把缺字段当致命错误。

### 错误码约定（见 `docs/API_SPEC.md` §0）

`plugin_not_installed`(404) / `no_permission`(403) / `token_invalid`(401) /
`rate_limited`(429) / `tshock_timeout`(504) / `tshock_unavailable`(502) /
`<插件>_error`(400，业务失败，`message` 原样给玩家)。

### 富文本

价格、解锁、备注等字段里可能含 Terraria 标签（`[i:..]` 物品图标、`[c/..:..]` 颜色）。
统一用 `web/src/components/ResultPanel.tsx` 的 `CommandOutput` 渲染（内部走
`lib/richtext.ts` 的 `parseRichText`）。

## 3. 新增一个插件模块的步骤

1. **读源码/实测**：拿到端点、参数、权限、返回字段（尤其注意**字段类型**：数组 vs 字符串、
   int vs bool）。
2. **后端客户端** `server/internal/tshock/<plugin>.go`：探测 + 各端点方法 + 容错类型。
3. **后端路由** `handlers.go`：`/api/<plugin>/capabilities` + 业务端点；业务错误用专属
   `<plugin>_error` 保留上游文案。
4. **传输层** `transport.ts`：加类型 + `BackendTransport` 方法；`httpTransport` / `mockTransport`
   / `web/src/test/playerStubs.ts` 同步。
5. **模块** `modules.ts`：加一个 `ModuleDef`；`SettingsPage` 自动列出（探测逻辑按 id 分派）。
6. **页面** `web/src/pages/<Plugin>Page.tsx`：参照同类页面（列表/网格 + 详情弹框）。
7. **测试**：后端 `*_test.go`（含真实字段形状的回归）、前端页面测试 + `modules.test`。
8. **文档**：新建 `docs/插件-<名>.md`（本模板，含插件版本 / 项目地址 / 用到的 REST API 与指令），
   并在本文件顶部「现有文档」列出。

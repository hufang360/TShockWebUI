# 计划 · 查找图格（在世界里定位「生命水晶」这类东西）

> 状态：**已实现（2026-10-26）**。功能说明见 [`功能-查找图格.md`](功能-查找图格.md)，验收见 `docs/记录-实现与验收.md`。
> 实际提取到 `items 262 / objects 84`；`lib/tiles.ts` 的搜索优先用 `dataset.tileNameById`（单一来源）。
> 后续三项（墙 / 液体、坐标 CSV、点坐标跳到 1:1）也已完成，见功能文档 §1。

## 1. 需求

在「查看世界」里按名字找图格，例如「生命水晶」，得到：**命中数量 + 坐标列表 + 在缩略图上标出来**。

## 2. 调查结论（决定方案的三条事实）

### 2.1 我们已经有全量的图格流解码能力

`worldThumb.ts` 为了渲染缩略图，本来就一趟解码 2000 万格（实测大世界 0.15 秒量级）。
定位 = 同一套解码里判断 `tileType === 目标 id` 并记录 `(x, y)`，**不需要新解析器**。

### 2.2 但「生命水晶」这种图格没有代表物品，中文名拿不到

- `data/tiles.json` 的显示名约定是「**代表物品**的本地化名」，拿不到才回退常量名（`tools/gen-tile-wall.mjs` 注释）。
- 生命水晶是**世界里生成、玩家不能放置**的图格：`TileID.Heart = 12`，`item` 字段为 `null`
  → 现在的界面会显示 `Heart`，用户搜「生命水晶」也搜不到。
- 游戏里它的地图图例名来自 **`Lang.BuildMapAtlas()`**：
  `_mapLegendCache[MapHelper.TileToLookup(12, 0)] = itemNameCache[29];`（`Terraria/Lang.cs:584`），
  也就是物品 29 =「生命水晶」。这类映射共 **436 条赋值 + 4 个循环**（树、罐子等）。

### 2.3 语言包里有 `MapObject` 分区，但我们的 loc 没导

`Terraria.Localization.Content.zh-Hans.Game.json` 根上有 `MapObject`（79 条：`Tree=树`、`Iron=铁`、`Pot=罐子`…），
我们生成的 `data/loc.*.json` 只导了 `ItemName / Prefix / LegacyMisc / Misc / NPCName / BuffName` 六节，
所以 `MapObject` 那 79 个名字（矿石、门、家具…）现在也用不上。

### 2.4 为什么不直接跑游戏里的 `BuildMapAtlas()`

它在 `Main.dedServ`（专用服务器）时**直接 return**，且依赖语言包已加载；
在 headless 的 `tools/gamedump` 里复现成本高、还容易和运行时行为漂移。
→ 改为**静态提取**源码里的映射规则（可重复生成、可核对），与其它数据的生成方式一致。

## 3. 方案

### 3.1 新增数据 `data/tile-names.json`

由新脚本 `tools/gen-tile-names.mjs` 从 `Terraria/Lang.cs` 的 `BuildMapAtlas()` 正则提取：

```json
{
  "meta": { "gameVersion": "1.4.5.8", "source": "Terraria/Lang.cs BuildMapAtlas()", "itemCount": N, "objectCount": M },
  "items":  { "12": 29, "13": 31, ... },      // 图格 → 图例名来自哪个物品
  "objects": { "28": "Pot", "6": "Iron", ... } // 图格 → MapObject 键
}
```

- 只取 **style 0**（同一图格的样式变体名通常相同；样式差异（如 `Chair` / `Toilet`）取第一个，够用）。
- 循环按源码展开：`IsATreeTrunk` → `Tree`；`for (k < 9)` 的罐子类 → 全部 style 都取 `Pot`。

### 3.2 loc 补 `MapObject` 分区

`data/loc.<culture>.json` 增加 `MapObject`（79 条），来自语言包根上的 `MapObject`
（同时把 `tools/gen-data.mjs` 的 loc 生成逻辑补上这一节，保证以后重新生成不丢）。

### 3.3 前端

| 件 | 内容 |
| --- | --- |
| 名字解析 | `lib/tiles.ts`：`tileDisplayName(dataset, id)` = `MapObject[key]` → `ItemName[代表物品]` → 常量名。**与游戏图例口径一致**，顺带修掉图格 12 显示 `Heart` 的问题（列表、地图分析、查找都用它） |
| 搜索 | `searchTiles(dataset, query)`：按「显示名 / 常量名 / id / 代表物品名」匹配，返回候选（含 id、名字、是否可以搜） |
| 定位 | `lib/save/worldFind.ts`：`findTiles(bytes, parsed, ids, { limit, onProgress })` —— 一趟解码，收集命中坐标；**上限 5000 条**并标记 `truncated`；支持多选 id 一起扫 |
| UI | 「查看世界」新增卡片「查找图格」：搜索框 + 候选列表 → 点一个开始扫描（进度条）→ 显示「命中 N 处」+ 坐标列表（前 200，可复制） + 「在缩略图上标记」开关 |
| 标记 | `WorldPanel` 增加可选 `markers`：在缩略图上叠加小方点（按 `width/thumb.width` 比例换算，不重画位图） |

### 3.4 性能与边界

- 大世界一趟扫描 ≈ 0.15 秒（与渲染同量级），按需触发，不在导入时做。
- 命中太多（如「石块」= 400 万处）时：**先算数量、只存前 5000 个坐标**，界面提示「只显示前 5000 处」。
- 空气/墙不在查找范围（只查图格）；未来可扩展「按墙找」。
- 结果不缓存到 localStorage（与其它本地文件功能一致）。

## 4. 验收

1. `data/tile-names.json` 真实数据测试：图格 12 → 物品 29 → 「生命水晶」；图格 6 → `Iron`；罐子 28 → `Pot`。
2. `findTiles` 用合成世界断言**精确坐标**与命中数量；`limit` 截断正常。
3. UI 测试：搜「生命水晶」→ 选中 → 命中数与坐标列表出现；「在缩略图上标记」开关渲染 marker 层。
4. 真实 demo 世界跑一遍：生命水晶 0 处（空白世界）不报错；石头能给出大量命中且被截断提示。
5. 全量 `vitest` / `tsc` / `build` / `oxlint` 通过。

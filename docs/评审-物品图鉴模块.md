## 1. 限额逻辑（上限 / 截断 / 缓存）审查

| 位置 | 限额 | 结论 |
| --- | --- | --- |
| `web/src/lib/itemFavorites.ts` | `ITEM_FAVORITES_LIMIT = 200` | 写满后 `addItemFavorite` **静默丢最旧**，UI 无任何提示。语义本身没问题（注释已写），但用户不知道「收藏到上限了」。建议：接近/达到上限时给一句 toast 或把上限放到设置里。 |
| `web/src/components/RecipePanel.tsx` | `MAX_ROWS = 60`（「N 条未显示」每次 +60） | **已修**：原来 `limit` 状态不随物品切换重置，上一个物品点了几次「加载更多」会带到下一个物品。现在用 `useEffect(..., [rows])` 在换物品时重置。 |
| `web/src/lib/pagination.ts` | `PAGE_SIZES = [50,100,200,360,500]`、`PAGE_SIZE = 100` | ✅ 没问题：`readDexPageSize()` 会校验是否在白名单里，非法值回落 100；`totalPages` / `clampPage` / `paginate` 都有单测。 |
| `web/src/lib/items.ts` | `searchItems(items, query, limit = 30)` | 指令编辑器用默认 30；**物品图鉴传的是 `tabItems.length`**，不截断。不是 bug，但两个调用方语义不同，容易误读——建议给图鉴调用处加注释。 |
| `web/src/lib/virtualGrid.ts` | overscan 2 行 | ✅ 边界（`count=0`、`scrollTop > totalHeight`、宽度未测量）都夹取正确；有单测。 |
| `GET /data/*`（后端 `handlers.go`） | `Cache-Control: public, max-age=3600`，**无 ETag** | **最容易让人误以为「数据不对」的一条**（也是 `docs/TODO.md` P2）：升级后浏览器最多 1 小时仍用旧的 `item-tips / item-stats / prefix-mods / prefix-sets`。新增的「基础值」说明 / 「可微分」/「最佳词缀评分」在旧缓存下会缺失或显示旧值。建议尽快按 P2 加 ETag + `no-cache`。 |
| 词缀下拉 | 只列「可滚且有效」的词缀 | 现在会按游戏规则**过滤掉对该物品无效的词缀**（伤害/攻速/蓝耗四舍五入后没变化、击退为 0 还给击退倍率）。所以下拉可能比 `prefix-sets.json` 少几项——这是**正确**的，不是丢数据。 |

## 2. 改进建议（按价值排序）

1. **物品详情加一个「速览」区块**：把「可微分」「最佳词缀」「基础值说明」这类**计算出来的**信息集中显示，而不是散在 tips 预览、词缀小框、tips 下方三处。现在信息是对的，但用户要「找」。
2. **最佳词缀可一键套用**：目前只展示「最佳词缀：传奇」+ 下拉里 ⭐/评分。可在旁边加一个按钮直接选中（选中后 tips 立即按该词缀重算）。
3. **微光分解做成可搜索/可筛选**：`canDecraft` 现在是物品级徽章；做成 tag 后可以像「可附魔」那样搜「可微分」。
4. **`/data/*` 加 ETag**（P2）：对图鉴体验、对「升级后数据不对」的体感都有直接收益。
5. **收藏上限提示**：见 §1。
6. **物品详情里「复制」的下拉**：默认 ID，可考虑记住用户上次选择（跨物品），现在每次打开都回到 ID。

> 不建议做的：把物品图鉴做成管理后台；在悬停提示里塞入非游戏内的标签（会破坏「游戏同款」的定位）。

## 4. 待确认（**不确定 / 我做了选择，请你拍板**）

1. **「可丢微光分解」的位置**：我放在**物品详情**（tips 下方、合成表上方），并按你说的换成了
   **5362（八音盒（以太），无 tips）图标 + 文字**，同时**移除了**配方行里的「不微光」。
   若你还要它出现在「悬停提示」「网格角标」或「可搜索 tag」里，请说。
2. **可微分的判定口径**：游戏分解要求 `物品堆叠数 ≥ 配方产出数`。
   我按「凑够一组即可分解」处理，并在 `decraftStack > 1` 时标注「每 N 个分解一次」（共 445 件，如火把箭矢×10、平台×2）。
   若你要严格「**单个**就能分解」，那 445 件都要排除。
   另：判定**忽略**世界进度锁（骷髅王前 / 石巨人前），也**忽略**猩红/腐化世界的配方差异；且**有微光转换的物品优先转换、不算可分解**（如火把 8 → 5353）。
3. **最佳词缀的口径**：用的是**游戏自身**的评分（`Item.BestPrefixValue` / `rolledPrefixIsTopTier`），它偏向伤害 / 暴击 / 攻速，
   **不**考虑镐速 / 蓝耗 / 射程 / 击退偏好。所以铁镐的「最佳」显示为**传奇**（游戏口径如此）。
   若你要「按挖矿速度」「按续航」「按射程」等玩家口味另算，需要你定义口径。
4. **词缀下拉顺序**：我改成了**按游戏评分从高到低**并显示评分（`1.760`）或饰品效果。若你要保留游戏原顺序，请说。
5. **「仅显示图标」默认改 true 的迁移**：`useLocalState` 会保留已存的值 → 之前手动关过的老用户仍是关。
   要不要强推（换 storage key / 一次性迁移）？
6. **金币**：`canDecraft=false`（有微光转换优先），符合游戏分支，但金币本身也不是合成材料——是否需要额外说明。
7. **「类型 tag」已按你说的「不确定就不做」暂缓**：见 §5。

## 5. 关于「类型 tag」（**暂缓，等你拍板**）

你举例想要的 tag（配饰 / 家具 / 机械 / 制作 / 材料 / 工具 / 光源）**不在同一处数据里**，现状如下：

| tag | 能不能拿到 | 数据源 |
| --- | --- | --- |
| 家具 | ✅ 能 | `item-groups.json` 的创意菜单过滤器 `furniture` |
| 配饰 | ✅ 能 | 过滤器 `accessories` / `accessoriesMisc`（或 `stats.accessory`） |
| 材料 | ✅ 能 | 过滤器 `materials`（或 `stats.material`） |
| 工具 | ✅ 能 | 过滤器 `tools`（或 `stats.pick/axe/hammer`） |
| 机械 | ✅ 能 | `TileID.Sets.Wiring.IsAMechanism/IsATrigger[item.createTile]`（现在已算 `wireable`，但没写进 `item-stats`） |
| 光源 | ⚠️ 可做但未做 | `Main.tileLighted[item.createTile]`（需要 gamedump 先调 `Initialize_TileAndNPCData`） |
| 制作 | ❓ 不确定 | 含义模糊：是「可制作」（有配方）？还是「制作材料」？还是「制作站」？——**没做** |

实测例子：
- 八音盒 562/563（八音盒（地表世界））：过滤器 = `furniture / accessories / materials`；`createTile=139`（在 `IsAMechanism` 里 → 机械）。
- 铜吊灯 106：过滤器 = `furniture`；`createTile=34`（也在 `IsAMechanism` 里）。
- 你期望的「吊灯 = 家具 + 光源」能凑出家具，但「光源」要额外导 `tileLighted`；而且按游戏口径吊灯还会被标成「机械」，与你举例不完全一致。

结论：**凑得出一套「游戏口径」的 tag，但与你举例的「维基口径」不能保证一致**（特别是「制作」「光源」）。
所以本轮**只做了你明确要的那部分（5362 图标 + 可丢微光分解）**，tag 暂缓。
如果你能确认 tag 的来源（游戏口径，还是维基口径）与具体集合，我再接。

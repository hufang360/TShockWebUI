# 发布流程（发版 checklist）

> 单一事实源。版本号 / 构建 / 部署的细节见 [`ARCHITECTURE.md`](ARCHITECTURE.md) §6，
> 常用命令见 [`开发速查.md`](开发速查.md)，真实客户端验收见 [`验收清单.md`](验收清单.md)。
>
> 原则：**先定稿文档 → 再全量验证 → 提交 → 打 tag → 推送 → 等 CI**。本仓库不会自动 push。

---

## 0. 版本号

- 来源：`web/package.json` 的 `version`（构建时注入前端 `__APP_VERSION__`，设置页底部展示）。
- 同一版本号需要一致的位置：
  - `web/package.json`、`web/package-lock.json`（2 处）
  - `plugin/WebUI/WebUI.csproj`（决定 `WebUI-<版本>.dll` 的资产名与 DLL 内版本）
  - `docs/插件-信使.md`、`docs/插件-物资申请.md` 的「插件版本」行（若本轮插件有改动）
- 改完跑 `make release-check`：会检查两份单版本文档是否齐备、版本号是否写对。
- **README 引用同步**：`README.md` / `README.en.md` 里的 release 下载地址（`releases/download/v<版本>/...`）、
  资产文件名（`tswui-<版本>-...` / `WebUI-<版本>.dll`）与 Docker 镜像 tag（`tshockwebui:<版本>`）
  必须改成当前版本；`make release-check` 会把它们与 `web/package.json` 的版本比对，有旧版本就报错。

## 1. 两份单版本文档（每个版本都必须有）

| 文件 | 内容 | 用途 |
| --- | --- | --- |
| `docs/changelog/<版本>.md` | 单版本、按功能模块的**详细**更新 | 仓库内归档 / 详细说明 |
| `docs/release/<版本>.md` | 单版本、**三段式**（新增 / 改进 / 修复） | GitHub Release 说明，直接给玩家看 |

```bash
make release-docs          # 按 web/package.json 的版本从模板生成（不覆盖已有文件）
# 或指定版本：scripts/new-release-docs.sh 0.1.0-rc.9
```

- 模板：`docs/changelog/_TEMPLATE.md`、`docs/release/_TEMPLATE.md`。
- 根目录 `changelog.md` 是**全量历史**；单版本 changelog 是它该版本的切片（内容以根为准，可多一句本轮重点）。
- 写作口径见 [`../AGENTS.md`](../AGENTS.md)「更新日志」：只写相对上一个已发布版本的**对外净变化**，
  删掉被后续改动推翻的中间态；小修小改合并，不逐条罗列。
- `docs/release/<版本>.md` 存在时，`release.yml` 会**直接用它作为 Release 说明**；不存在才退回自动生成。

## 2. 根 changelog 定稿

- `## 未发布（vX.Y.Z）` → `## YYYYMMDD（vX.Y.Z）`（发版当天日期，**新的在上**）。
- 合并 / 删除内部迭代，按「页面 → 全局」梳理；写法回到用户视角。
- `docs/changelog/<版本>.md` 与这一段保持一致。

## 3. 文档检查

```bash
make release-check     # 两份单版本文档 + 三段标题 + 版本号
make docs-check        # 全仓 md 相对链接死链（跳过模板与构建产物）
```

另外核对：

- `设计原则与约束.md` §4.6 新增的 localStorage / IndexedDB 键是否已登记；
- `TODO.md` 里与本轮相关的「待定 / 待验证」是否已更新；
- 文档命名符合 [`README.md`](README.md) 的约定（功能 / 页面 / 插件 / 计划 / 记录）。

## 4. 代码侧全量验证

```bash
cd server && go vet ./... && go test -race ./... -count=1
cd web && npx tsc -b && npx oxlint
cd web && npx vitest run --maxWorkers=10        # 并发上限见 AGENTS「验证强度」
cd web && npm run build
cd plugin/WebUI && dotnet build -c Release
SKIP_WEB=1 SMOKE=1 VERSION=<版本> scripts/build-binary.sh
VITE_TRANSPORT=mock VITE_BASE=/TShockWebUI/ npx vite build   # Pages 演示（之后恢复正式构建）
```

Docker 交付镜像：本机有外网时 `docker build --build-arg VERSION=<版本> -t tswui:<版本>-local .`；
无外网则记录为「由 CI 验证」，或按 `记录-实现与验收.md` 的做法用本地缓存基础镜像做等价离线构建。

## 5. 记录

在 [`记录-实现与验收.md`](记录-实现与验收.md) 追加一节：

```
## vX.Y.Z 发版前检查与整理（YYYY-MM-DD）
```

写清：版本号 / changelog 压缩了什么 / 文档检查 / lint 与测试数字 / 构建与冒烟结果 / 仍需人工的项。

## 6. 提交、打 tag、推送

```bash
git add -A
git commit -m "release: vX.Y.Z"
git tag -a vX.Y.Z -m "vX.Y.Z"
git push origin master
git push origin vX.Y.Z        # 别用 --tags（会带上本地其它 tag）
```

> tag 推送后触发 `release.yml`。预发布（版本号带 `-rc.N`）会标成 Pre-release，Docker 不打 `:latest`。

## 7. 等 CI 与发布后核对

1. `release.yml` 全绿后核对资产：4 个平台二进制 + `WebUI-<版本>.dll` + `SHA256SUMS`，
   以及 GHCR / Docker Hub 的 `<版本>` 标签。
2. 下载资产实测：`shasum -a 256 -c SHA256SUMS`、`./tswui-<版本>-<平台> -version`、
   镜像实跑 `/healthz` 与 `/`。
3. Release 说明应来自 `docs/release/<版本>.md`（可在网页上核对），必要时 `gh release edit`。
4. 把实际发布与产物实测追加到 `记录-实现与验收.md`（含资产清单、镜像大小、Pages 地址）。
5. 真实客户端 / Windows 相关项按 [`验收清单.md`](验收清单.md) 继续跟进，不阻塞发版。

## 8. 回退

- **tag 已推但 CI 没产出任何资产**：可以删远端 tag、修好后重新打；
  `git push origin :refs/tags/vX.Y.Z`，然后重新 `git tag -a`、`git push origin vX.Y.Z`。
- **已经产出资产 / 已发布**：不要强推同一个 tag；发一个新版本（`-rc.N+1`）。
